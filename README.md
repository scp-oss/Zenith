# Zenith

Автоподборщик-генератор стратегий DPI-обхода для [z2r](https://github.com/AloofLibra/z4r)
(zapret2). Не подменяет [z2r_autobench](https://github.com/scp-oss/z2r_autobench) —
z2r_autobench перебирает и ранжирует уже существующие в z2r стратегии
(`--lua-desync=circular_locked:key=N`), а Zenith **генерирует новые**:
мутирует и скрещивает параметры (fake/split/disorder/ttl/fooling/blob) вместо
того чтобы выбирать из готового списка.

Найденные Zenith'ом рабочие геномы применяются на живом сервере тем же
мостом, что уже использует Discord-бот в z2r_autobench —
`set_strategy_cli.sh set/get/max`. Zenith не трогает `/opt/zapret2`
напрямую.

## Почему отдельным проектом, а не частью z2r_autobench

z2r_autobench — bash-обвязка вокруг локов z2r (`locked.tsv`), без своего
состояния кроме файлов на диске. Генератору нужна БД (история мутаций,
родословная геномов, статистика по нескольким серверам/провайдерам) —
принципиально другой слой, поэтому отдельный репозиторий, свой жизненный
цикл. Устанавливается на сервер так же, как `z2r_test-voice-bot` — через
пункт меню z0r, в `/opt/z2r_autobench/Zenith`.

БД — отдельная, необязательно docker'ная часть: при установке можно
поднять MySQL сами (`docker compose`, локально) либо подключиться к уже
существующей (`ZENITH_DB_MODE=external` в `.env`, без Docker вообще).
Сам генератор всегда работает прямо на хосте, не в контейнере — ему нужно
вызывать `set_strategy_cli.sh` и трогать локальные файлы z2r_autobench,
пробрасывать это внутрь контейнера ради одной команды смысла нет.

## Принципы генерации (для контекста, не как истина в последней инстанции)

1. **Подбор кандидата не случайным перебором, а через UCB** (upper confidence
   bound — классический multi-armed bandit), чтобы не топтаться по заведомо
   плохим веткам параметров. Плюс crossover — скрещивание двух удачных
   геномов, не только мутация одного. Плюс whitelist валидных комбинаций
   режимов, собранный из существующих рабочих стратегий, чтобы мутация не
   рожала синтаксически бессмысленные сочетания. Плюс кэш по хэшу
   конфига — не тестировать дважды один и тот же геном (заодно снижает
   частоту запросов).
2. **Мутация по цепочке эскалации, а не вслепую.** Семейств desync-режимов
   немного (fake/сегментация/подмена wsize/поддельный synack), а параметры
   внутри семейства — это гонка вооружений с DPI: TTL не проходит → autottl
   → DPI научился детектить кривой TTL → tcp_ts → tcp_ts ломает сайты →
   seqovl+tcp_md5 → известные фейки палятся → динамически захваченный
   ClientHello → DPI научился собирать сегменты → сегментируем и фейк, и
   реальный трафик, и перемешиваем. Мутация должна приоритетно пробовать
   следующий шаг по этой цепочке, а не случайную соседнюю комбинацию.
3. **Защита от эскалации ТСПУ — не опция, а обязательное условие с самого
   начала.** При плотном переборе многих стратегий подряд есть риск не
   "стратегия не работает", а "ТСПУ начал приглядываться" — генератор
   технически создаёт кандидатов на порядки быстрее ручного перебора,
   поэтому нужны адаптивная пауза, circuit breaker и самообслуживающийся
   пул тестовых доменов с самого старта (см. `ban_events`/`domain_pool` в
   схеме БД).

## Как тестируются новые геномы, не трогая боевой zapret2

`set_strategy_cli.sh`/`locked.tsv` (мост в z2r_autobench) — это переключатель
между УЖЕ существующими в конфиге пронумерованными блоками
`--lua-desync=...`, мгновенный именно потому, что ничего не переписывает.
Для только что сгенерированного генома, которого в конфиге ещё нет,
переключать нечего.

Вариант "дописывать геном в боевой конфиг и рестартовать nfqws2" — рабочий,
но означает рестарт боевого процесса на каждую мутацию, а это то же самое,
от чего защищает вся тема с банами/эскалацией ТСПУ, только опаснее, потому
что рвёт реальный трафик, а не только тестовый.

Вместо этого — **`sandbox/`**: второй, полностью изолированный `nfqws2`,
не связанный с `/opt/zapret2` вообще. Узкое iptables-правило заворачивает
в его собственную `NFQUEUE` только TCP-трафик отдельного системного юзера
(`zenith-sandbox`) — тестовые пробы Zenith идут от этого юзера, весь
остальной трафик хоста, включая боевой zapret2, правило не видит. Каждый
геном тестируется перезаписью конфига песочницы и её дешёвым перезапуском
— боевой процесс это не задевает совсем. Подробности и обязательный
смоук-тест перед тем как доверять — `sandbox/README.md`.

Если этот подход на практике окажется непрактичным (например, из-за
особенностей `--queue-bypass`/owner-match в конкретном окружении) —
резервный вариант 1 (дописывать в боевой конфиг) остаётся задокументирован
выше, но пока не реализован.

**Живой инцидент 2026-08-07, разобран до настоящей первопричины.** Геном
`hostfakesplit:midhost=midsld:disorder_after:tcp_ack=-66000:tcp_ts_up`
(RKN_TLS) — 13/13 успехов в песочнице, продвинут в прод через
`promote.py` как strategy=43 — на боевом трафике `meduza.io` стабильно
проваливался (`000 0`, 3/3), `rutor.info` продолжал работать. Первая
гипотеза (узкий фильтр песочницы без `--hostlist=`/`--payload=`) была
частично верной и исправлена (см. ниже про `genome.PROFILE_FILTERS`), но
**настоящая причина оказалась другой и гораздо проще**: боевой
`nfqws2`/`zapret2` не перезапускался ни разу с 2026-08-04 — новый блок
`strategy=43` физически никогда не попадал в память работающего процесса.
z2r-функция `circular_locked` (`/opt/zapret2/z2r_lib`-соседний lua-код,
`orchestra/locked.lua`) на каждое соединение сверяет `locked.tsv` с
`ctstrategy` — максимальным номером стратегии, который она увидела в
ПЛАНЕ ТЕКУЩЕГО ПРОЦЕССА при первом коннекте к этому хосту (кэш без TTL,
живёт до рестарта процесса). Раз `strategy=43` в память так и не попал,
`locked=43 > ctstrategy(≤42)` было ложным на каждом коннекте, и
`circular_locked` молча откатывался на `strategy=1` — а strategy=1
(общий шаблон `z2r_tcp_tls_common`) уже был проверен в этой же сессии и
не работает конкретно на `meduza.io`. Геном strategy=43 в реальности
**вообще ни разу не применялся** — сравнение шло со strategy=1, не с
нашим геномом. После честного `systemctl restart zapret2` (с уже
залоченной strategy=3, для страховки) и повторного
`set_strategy_cli.sh set 3 tls 43` — geнoм отработал 6/6 на обоих
доменах. Ложной тревоги при живой проверке (см. ниже правило "любой
промоушен обязателен проверять живым трафиком") в итоге не случилось бы,
если бы рестарт произошёл ДО первого промоушена — сама многоступенчатая
проверка сработала правильно, просто не с первой попытки.

Практический вывод, не специфичный для Zenith: `set_strategy_cli.sh set`
меняет только `locked.tsv` — это НЕ горячее применение нового блока
стратегии, а переключатель среди УЖЕ загруженных в память процесса.
Продвижение новой (никогда раньше не запускавшейся) стратегии ВСЕГДА
требует подтверждённого перезапуска `nfqws2`/`zapret2` (не "как обычно",
а с проверкой `systemctl status zapret2` → `Active: ... since <только что>`)
между вставкой блока в конфиг и `set_strategy_cli.sh set` — иначе
переключение молча откатывается на strategy=1 без единой ошибки в логах.

Отдельно исправлено (не первопричина, но реальный и полезный фикс):
`genome.PROFILE_FILTERS` теперь хранит РЕАЛЬНЫЙ боевой фильтр каждого
профиля (полный список портов, `--hostlist=`/`--hostlist-exclude=`,
`--payload=`, сверено построчно с `/opt/zapret2/config`), и
`sandbox_apply.py` переписывает эти строки в конфиге песочницы при
каждом применении генома/control'а, а не один фиксированный
`--filter-tcp=443 --filter-l7=tls`. Песочница по-прежнему не
воспроизводит `--out-range=`/`--in-range=`-слоение и саму
`circular_locked`-логику (тестирует геном напрямую, в обход
per-host-кэша) — поэтому **любой промоушен всё равно обязателен
проверять живым трафиком на ВСЕХ доменах профиля, ПОСЛЕ подтверждённого
рестарта**.

## VOICE_UDP — замена ручного Discord-бота

До этого VOICE_UDP (профиль 6) ранжировался вручную через
`z2r_test-voice-bot` (`/voice_rank`) — тот же по духу инструмент, что
`rank_strategies.sh` для TCP-профилей до Zenith: перебирает уже готовые
стратегии, ничего не генерирует. Теперь Zenith генерирует и тестирует
VOICE_UDP-геномы сам, тем же циклом, что и TCP-профили:

- Геном-модель: `fake`/`udplen`/`send` + `ipfrag_pos_udp`/`ipfrag_disorder`
  (`genome.py`), блобы -- `genome.UDP_FAKE_BLOBS`, все семейства и блобы
  сверены построчно с реальным профилем 6 в `/opt/zapret2/config`
  (`--filter-udp=443,...,50000-50099,...` + `circular_locked:key=6:
  proto=udp:allow_nohost=1` -- нет SNI у STUN/discord_ip_discovery,
  профиль матчится по `key`, не по хосту). Осознанно НЕ включает
  `out_range=` -- встречается в реальном конфиге, но такого
  per-instance аргумента нет в манулe zapret2 (только CLI-уровневый
  `--out-range=`), не мутируем то, что не можем объяснить документацией.
- Тестовый клиент (`orchestrator/voice_tester.py`) — **без своего
  Discord-бота/токена**: дёргает уже работающий и залогиненный
  [z2r_test-voice-bot](https://github.com/scp-oss/z2r_test-voice-bot)
  через его локальный HTTP (`POST /probe`, `{"lua_desync_lines": [...]}`,
  см. его README "Интеграция с Zenith"). Один бот, один токен, один
  владелец — по явному запросу, вместо второй параллельной Discord-сессии.
  Бот сам применяет присланный геном в СВОЕЙ песочнице (той же, что у
  остальных профилей Zenith — `sandbox/nfqws2_sandbox.conf`) и тестирует
  реальным Discord voice UDP-подключением (gateway handshake + IP
  discovery, не имитация). Метрика — время подключения в мс (не байты,
  байтов тут нет).
- Для этого бот должен работать от ОТДЕЛЬНОГО юзера `zenith-voice-bot`
  (не `zenith-sandbox` -- тот занят curl-проверками TCP-профилей; живой
  инцидент 2026-08-07: обычный HTTPS-трафик бота, попав под то же
  широкое TCP-правило, вис из-за особенности nfqws2's TLS-реассемблинга
  без единого `--filter-tcp=` в конфиге) и тестировать через песочницу,
  а не боевой `locked.tsv`, как раньше — подробности и команды переезда
  в README самого `z2r_test-voice-bot` ("Песочница, не прод").
- `setup_sandbox.sh` теперь создаёт и `zenith-voice-bot` тоже — узкое
  UDP-правило только на конкретные порты голосового профиля (не весь
  TCP/UDP, в отличие от правила `zenith-sandbox`).

```bash
sudo ./sandbox/setup_sandbox.sh   # повторно, создаст zenith-voice-bot и его правило если ещё нет

# z2r_test-voice-bot должен быть переведён на юзера zenith-voice-bot и
# запущен (см. его README) -- без этого VOICE_UDP-тесты не пройдут.

cd orchestrator
venv/bin/pip install -r requirements.txt
sudo venv/bin/python3 main.py --profile VOICE_UDP --rounds 20
```

## Веб-панель и мульти-провайдерный sync (`panel/`)

По запросу: единая точка для (1) органов управления, (2) обзора стратегий
по провайдерам, (3) истории мутаций конкретных геномов, и (4) накопления
опыта так, чтобы смерть одной ноды его не теряла.

**Топология -- hub-and-spoke, не общая MySQL и не mesh.** Панель живёт
НА прод-сервере и делит с локальным `orchestrator/` ту же MySQL напрямую
(своей отдельной БД у панели нет). Удалённые ноды (ВМ ростелеком/МТС и
т.п.) MySQL-доступа к панели НЕ получают вообще -- порт наружу не
открывается. Вместо этого каждая удалённая нода:
- после `main.py` шлёт `sync_client.py push` -- HTTP POST снапшота своих
  `genomes`+`genome_scores` на панель, с собственным Bearer-токеном
  (выдаётся на странице `/nodes`, показывается один раз, в БД хранится
  только его sha256);
- может `sync_client.py pull` -- забрать глобальный топ геномов со ВСЕХ
  нод как кандидатов (`source='sync_import'`), чтобы затравить свой
  локальный UCB чужими находками.

Это сознательный уход от roadmap-пункта "вынести MySQL за localhost"
(п.6 ниже) в сторону более безопасной схемы: если панель временно
недоступна, локальный `main.py` каждой ноды продолжает работать как ни в
чём не бывало (своя БД, своя песочница) -- зависимость только на момент
sync, не на каждый раунд генерации.

### Bootstrap для новой ноды -- "разворачиваем на очередном сервере"

По прямому запросу: вместо того, чтобы каждая новая нода начинала с нуля
(сиды -> мутации -> докрутка, как раньше), она сперва спрашивает у панели,
что уже известно рабочим:

```bash
cd orchestrator
venv/bin/pip install -r requirements.txt
python3 bootstrap.py --profile RKN_TLS
```

`GET /api/v1/sync/bootstrap` на панели возвращает два яруса кандидатов
(`panel/db.py::bootstrap_candidates`):
1. **provider** -- геномы со 100%-успехом у ЭТОГО ЖЕ провайдера (по
   `environments.provider` токена ноды) на других нодах;
2. **universal** -- геномы со 100%-успехом сразу у 2+ разных провайдеров
   -- не завязаны на конкретную DPI одного оператора, более общий паттерн.

`bootstrap.py` не копирует чужие цифры вслепую -- каждый кандидат реально
проверяется в локальной песочнице (по 3 попытки, та же логика применения,
что у обычных геномов в `main.py`). Подтвердившиеся остаются в БД как
обычные геномы (`main.py` дальше докрутит их через genome-level UCB);
если ничего не подтвердилось -- вывод так и говорит: "DPI этого
провайдера не похожа на уже виденные", обычный путь -- `main.py` с сидами.

### База знаний по семействам (не по конкретным геномам)

Конкретные параметры (имена блобов, TTL) у каждого провайдера свои, но
`family`+`fooling`+`ttl_mode` -- уже переносимый уровень паттерна
("fake с autottl", "multidisorder+seqovl" и т.п., как и описано в
"Принципы генерации" п.2 выше). Страница `/knowledge` на панели --
group-by этого уровня по всем профилям/провайдерам разом
(`panel/db.py::knowledge_family_rollup`), с колонкой "сколько разных
провайдеров" -- чем больше, тем более общий, не-провайдер-специфичный
приём. Копится сама по себе по мере того, как ноды синкаются -- ручного
курирования не требует.

### Установка панели

```bash
# 1. Миграция БД, если ставится на УЖЕ работающую (не свежую) БД:
mysql -u zenith -p z2r_genome < db/migrations/001_panel_sync.sql

# 2. Отдельный системный юзер под панель -- ей нужен доступ к MySQL
#    (по паролю из .env, как у orchestrator) и read-only sudo на
#    set_strategy_cli.sh get/max для страницы /controls (НИКОГДА set --
#    панель ничего не применяет в боевой конфиг сама, см. panel/main.py
#    docstring "Границы ответственности панели").
sudo useradd --system --no-create-home --shell /usr/sbin/nologin zenith-panel
echo 'zenith-panel ALL=(root) NOPASSWD: /usr/bin/bash /opt/z2r_autobench/set_strategy_cli.sh get *, /usr/bin/bash /opt/z2r_autobench/set_strategy_cli.sh max *' \
  | sudo tee /etc/sudoers.d/zenith-panel
sudo chmod 440 /etc/sudoers.d/zenith-panel

cd panel
python3 -m venv venv && venv/bin/pip install -r requirements.txt
venv/bin/python3 gen_password_hash.py   # впиши результат в Zenith/.env как PANEL_ADMIN_PASSWORD_HASH
python3 -c 'import secrets; print(secrets.token_hex(32))'   # -> PANEL_SESSION_SECRET в .env

sudo cp zenith-panel.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now zenith-panel
```

**Слушает на внешнем порту (`PANEL_PORT`, по умолчанию 8766) по прямому
запросу** -- логин/пароль защищает вход, но сам HTTP по умолчанию БЕЗ TLS
(пароль и сессионная cookie идут в открытом виде). Для боевого
использования настоятельно рекомендуется поставить перед панелью reverse
proxy с HTTPS (nginx + certbot/Let's Encrypt) -- сама панель этого не
делает, вне её зоны ответственности (нет exec-доступа для настройки nginx
отсюда, только эти инструкции).

Добавить удалённую ноду: `/nodes` в UI -> имя+провайдер -> токен
показывается один раз -> на удалённой ноде в `.env`:
```
PANEL_URL=http://<адрес-панели>:8766
PANEL_NODE_TOKEN=<токен>
```

## Статус: работает v1, с упрощениями

- `db/schema.sql` — схема MySQL, теперь с `genomes.profile` (отдельный
  пул генома на профиль, не шарится).
- `docker-compose.yml` — только MySQL, только для `ZENITH_DB_MODE=docker`.
- `sandbox/` — изолированный nfqws2 для тестирования геномов, со
  смоук-тестом.
- `orchestrator/` — рабочий цикл: сиды → мутации по UCB1 (приоритет по
  цепочке эскалации для ещё не опробованных операторов) → применение в
  песочнице → тест реальным коннектом → запись в `experiments`/
  `genome_scores`/`operator_stats` → простой circuit breaker (N разных
  геномов подряд провалились на одном домене → пауза + `ban_events`,
  а не "стратегия не работает"). Плюс `sync_client.py`/`bootstrap.py` —
  синк с панелью и первый запуск на новой ноде (см. ниже).
- `panel/` — веб-панель (FastAPI): обзор по профилям/нодам, история
  мутаций конкретного генома, read-only статус боевых стратегий, база
  знаний по семействам, и sync-хаб (push/pull/bootstrap API для
  удалённых нод) — см. "Веб-панель и мульти-провайдерный sync" ниже.

**Упрощения v1** (см. `orchestrator/main.py` docstring):
- `crossover()` в `mutate.py` есть, но в основной цикл ещё не подключена.
- Продвижение созревшего генома в боевой конфиг z2r (`promote.py`) готовит
  готовый блок конфига + команду `set_strategy_cli.sh`, но НЕ применяет
  их сам (у Zenith нет exec-доступа к боевому серверу) — человек вставляет
  блок и проверяет запуск руками.

## Запуск

```bash
cp .env.example .env
# поменять пароли, и либо оставить ZENITH_DB_MODE=docker:
docker compose up -d
# либо поставить ZENITH_DB_MODE=external и прописать MYSQL_HOST/MYSQL_PORT
# под уже существующую БД — тогда docker compose не нужен вообще.

sudo ./sandbox/setup_sandbox.sh   # один раз, см. sandbox/README.md (обязателен смоук-тест!)

cd orchestrator
python3 -m venv venv && venv/bin/pip install -r requirements.txt
sudo venv/bin/python3 main.py --profile YT_TLS --rounds 20

# сравнить с боевой ручной стратегией (несколько попыток на каждом домене
# профиля, пишет оба результата в БД, не только печатает):
sudo venv/bin/python3 compare_control.py --profile YT_TLS --trials 5

# подготовить блок конфига + команду переключения для лучшего найденного
# генома (сам НИЧЕГО не применяет — только печатает, что вставить и
# выполнить руками):
sudo venv/bin/python3 promote.py --profile YT_TLS --after-strategy 42
```

`main.py` пишет root'ом (нужен для песочницы и `sudo -u zenith-sandbox`) —
если `sudo -u` в твоём окружении спрашивает пароль даже от root, добавь
`zenith-sandbox` в `/etc/sudoers` с `NOPASSWD` или запускай без `sudo -u`
в `tester.py`, раз сам `main.py` уже root.

## Требования

- Docker + Docker Compose v2 — только для `ZENITH_DB_MODE=docker`. Для
  `external` не нужен вообще, но нужен клиент `mysql` на хосте.
- Продакшен-сервер остаётся источником истины по production-стратегиям
  (`z2r_autobench`/`locked.tsv`) — Zenith только предлагает и тестирует
  новых кандидатов, финальное применение — через уже существующий
  безопасный путь (`set_strategy_cli.sh`).
- Для VOICE_UDP — работающий `z2r_test-voice-bot` (см. раздел выше и его
  README), своего Discord-бота/токена Zenith не заводит.
