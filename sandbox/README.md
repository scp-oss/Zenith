# Песочница для тестирования геномов

Изолированный второй `nfqws2`, полностью отдельный от боевого
`/opt/zapret2`. Нужен, чтобы Zenith мог опробовать только что
сгенерированный (ещё нигде не прописанный) геном без перезапуска
боевого процесса и без риска для реального трафика — см. обсуждение в
основном README, раздел про архитектуру генератора.

**Как это работает:** узкое `iptables`-правило заворачивает в отдельную
`NFQUEUE` только TCP-трафик от одного системного юзера (`zenith-sandbox`).
Тестовые пробы Zenith делаются от этого юзера — значит только они и
попадают в песочный `nfqws2`. Весь остальной трафик хоста, включая
боевой zapret2, правило не видит и не трогает.

## Установка (один раз)

```bash
sudo ./setup_sandbox.sh
```

Дальше **обязательно** проверь глазами, прежде чем доверять:

```bash
iptables -t mangle -S | grep zenith-sandbox
```

Должна быть ровно одна строка вида:

```
-A OUTPUT -m owner --uid-owner zenith-sandbox -p tcp -j NFQUEUE --queue-num <N> --queue-bypass
```

## Запуск/остановка

```bash
sudo ./start_sandbox.sh
sudo ./stop_sandbox.sh
```

`start_sandbox.sh` безопасно перезапускать сколько угодно раз — именно
так его будет дёргать оркестратор перед каждым тестом нового генома.

## Смоук-тест перед тем как доверять

1. Запусти песочницу: `sudo ./start_sandbox.sh`
2. Пробный запрос ОТ ИМЕНИ zenith-sandbox (должен пройти через nfqws2-песочницу):
   ```bash
   sudo -u zenith-sandbox curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
     --max-time 5 https://ЗАБЛОКИРОВАННЫЙ_ДОМЕН/
   ```
3. Тот же запрос от ОБЫЧНОГО юзера (НЕ должен ничем отличаться от
   поведения без песочницы вообще — подтверждает изоляцию):
   ```bash
   curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
     --max-time 5 https://ЗАБЛОКИРОВАННЫЙ_ДОМЕН/
   ```
4. Проверь, что песочный nfqws2 вообще видел трафик:
   ```bash
   tail -50 nfqws2_sandbox.debug.log
   ```
   Если там пусто — значит трафик до него не долетает (правило не
   сработало) и всё дальнейшее тестирование геномов будет ложным
   "не работает".
5. Останови: `sudo ./stop_sandbox.sh`

Если шаг 2 не показал улучшения по сравнению с шагом 3 — значит
что-то не так с правилом/юзером/очередью, разбираться до того, как
подключать сюда генератор, а не после.

## Откат

```bash
sudo ./teardown_sandbox.sh
```

Останавливает песочный nfqws2, снимает ровно то iptables-правило, что
поставил `setup_sandbox.sh`, спрашивает про удаление юзера.

## Файлы

- `setup_sandbox.sh` / `teardown_sandbox.sh` — разовая инфраструктура
  (юзер, очередь, iptables-правило).
- `start_sandbox.sh` / `stop_sandbox.sh` — жизненный цикл процесса,
  дёргается часто (в перспективе — оркестратором на каждый геном).
- `nfqws2_sandbox.conf.template` — шаблон конфига (в git). Живой
  `nfqws2_sandbox.conf` генерится из него при первом старте и дальше
  переписывается оркестратором под конкретный геном — в git не входит
  (см. `.gitignore`), как и `queue_num`/`.pid`/`.debug.log`.
